# پیش‌بینی فروش فروشگاه‌های Favorita

پیش‌بینی چندافقی تقاضای خرده‌فروشی برای Corporación Favorita (اکوادور) — به‌عنوان یک مطالعه‌ی موردی کامل در تشخیص *چرایی* شکست مدل در بخش‌های خاص، نه صرفاً ساخت مدلی که به‌طور میانگین امتیاز خوبی می‌گیرد، **و تبدیل آن مدل به یک سیستم کاربردی و قابل‌استقرار که یک کاربر کسب‌وکاری غیرفنی هم واقعاً بتواند اجرایش کند.**

## چرا این پروژه

بیشتر پروژه‌های نمونه‌کار پیش‌بینی، در همان مرحله‌ی «مدل آموزش‌دیده در یک نوت‌بوک» متوقف می‌شوند. این پروژه فراتر می‌رود: **یک مدل اعتبارسنجی‌شده، تشخیص مستندشده‌ی نقاط ضعف آن (در ادامه)، و یک پایپ‌لاین استقرار واقعاً کاربردی** — دریافت داده، لایه‌ی تصمیم کسب‌وکاری، یک REST API، یک Container داکر، مانیتورینگ سبک، و یک صفحه‌ی وب ساده که کاربر غیرفنی بدون لمس هیچ کدی می‌تواند اجرایش کند.

- 📊 **مدل**: WAPE برابر ۱۲.۴۴٪، ۶۴٪ خطای کمتر نسبت به baseline ساده، به‌همراه یک لایه‌ی برچسب‌گذاری اطمینان اعتبارسنجی‌شده برای پیش‌بینی‌های کم‌اعتماد (جزئیات در ادامه)
- ⚙️ **پایپ‌لاین**: دریافت داده ← اعتبارسنجی ← مهندسی فیچر ← پیش‌بینی ← تصمیم کسب‌وکاری (ریسک کمبود/مازاد موجودی)، قابل‌اجرا سرتاسری با یک دستور
- 🌐 **Serving**: FastAPI + Docker، به‌همراه یک صفحه‌ی وب بدون‌نیاز-به-کد برای کاربر کسب‌وکاری — یک تاریخ انتخاب کن، دکمه را بزن، خلاصه‌ی پیش‌بینی به زبان ساده و یک گزارش قابل‌دانلود بگیر
- 📈 **مانیتورینگ**: هر اجرای پایپ‌لاین ثبت می‌شود (موفقیت/شکست، مدت‌زمان، تعداد خروجی‌ها)

👉 برای توضیح کامل به بخش [پایپ‌لاین استقرار در محیط عملیاتی](#deployment-pipeline-fa) مراجعه کنید، یا برای مطالعه‌ی بخش مدل‌سازی ادامه دهید.

## مسئله‌ی کسب‌وکار

خرده‌فروشان برای برنامه‌ریزی موجودی، نیروی انسانی و تبلیغات، به پیش‌بینی دقیق تقاضا نیاز دارند. مدلی که *به‌طور میانگین* دقیق است، می‌تواند برای زیرمجموعه‌ای از روزها که از نظر عملیاتی مهم‌ترند — یعنی جهش‌های فروش با حجم بالا — به‌شدت نادرست عمل کند. در این روزها، کم‌برآوردی به معنای اتمام موجودی و از دست رفتن درآمد است.

این پروژه فروش روزانه را برای ۱ تا ۱۵ روز آینده، برای هر ترکیب فروشگاه–خانواده‌ی محصول در زنجیره‌ی Favorita، با استفاده از یک مدل XGBoost چندافقی مستقیم پیش‌بینی می‌کند. تمرکز اصلی تحلیل صرفاً «ساخت یک مدل» نیست، بلکه **یافتن، توضیح، و اندازه‌گیری اینکه کجا و چرا مدل کمتر قابل‌اتکاست** و ساخت مکانیزمی برای علامت‌گذاری خودکار این عدم‌اطمینان است.

## نتایج کلیدی

- **WAPE کلی روی داده‌ی اعتبارسنجی: ۱۲.۴۴٪** (MAE برابر ۵۹.۲، RMSE برابر ۲۱۱.۷) در افق پیش‌بینی ۱۵ روزه، ارزیابی‌شده روی چهار نقطه‌ی شروع پیش‌بینی مجزا.
- **۶۴٪ خطای کمتر نسبت به baseline ساده‌ی تداومی** (WAPE برابر ۳۴.۲۲٪) و **۲۷٪ خطای کمتر نسبت به baseline فصلی-هفتگی** (WAPE برابر ۱۶.۹۹٪) — جدول زیر را ببینید.
- **پیش‌بینی‌های با اطمینان بالا (۶۷٪ از حجم دم توزیع) به WAPE برابر ۱۰.۴۶٪** و نرخ کم‌برآوردی شدید فقط **۰.۴۲٪** می‌رسند.
- **پیش‌بینی‌های با اطمینان پایین، نرخ کم‌برآوردی شدید ۱۵.۲۲٪** دارند — ۳۶ برابر بیشتر از پیش‌بینی‌های با اطمینان بالا — که به‌طور خودکار توسط یک لایه‌ی اعتبارسنجی پس‌از-پیش‌بینی (در ادامه توضیح داده شده) شناسایی می‌شود، بدون تغییر در خود مدل.
- تشخیص داده شد که جهش‌های بزرگ فروش عمدتاً در ترکیب‌های خاص فروشگاه/خانواده‌ی محصول (عمدتاً خانواده‌ی `CLEANING`، نوع فروشگاه `C`) متمرکز هستند و از طریق آزمون فرضیه‌ی هدفمند، تبلیغات (promotion) به‌عنوان علت رد شد.

### مقایسه با Baseline

| مدل | میانگین WAPE (روی ۳ نقطه‌ی شروع پیش‌بینی، افق ۱۵ روزه) |
|---|---|
| Naive (تداومی) | ۳۴.۲۲٪ |
| Weekly Seasonal Naive | ۱۶.۹۹٪ |
| **XGBoost (این پروژه)** | **۱۲.۴۴٪** |

baseline فصلی-هفتگی (آخرین مقدار مشاهده‌شده برای همان روز هفته) خودش برای داده‌ی خرده‌فروشی baseline نسبتاً قوی‌ای است، چون چرخه‌ی تقاضای هفتگی را در بر می‌گیرد. با این‌حال، مدل XGBoost همچنان خطای خود را بیش از یک‌چهارم کاهش می‌دهد — عمدتاً با یادگیری الگوهای بین‌سری (فروشگاه، خانواده، خوشه) و سیگنال‌های روند/نوسان‌پذیری بلندمدت که یک جستجوی فصلی تک‌سری نمی‌تواند آن‌ها را ثبت کند.

## رویکرد

### ۱. تحلیل اکتشافی داده (EDA)
توزیع فروش، روند، و فصلی‌بودن (سالانه، ماهانه، هفتگی) قبل از هر تصمیم مدل‌سازی بررسی شد تا الگوهای تقاضا درک شوند.

### ۲. مهندسی فیچر
- **فیچرهای تقویمی**: روز هفته، ماه، تعطیلات ملی/منطقه‌ای/محلی، جمعه سیاه، دوشنبه سایبری، روز مادر (با نگاشت صحیح بر اساس محدوده‌ی جغرافیایی، برای جلوگیری از نشت اطلاعات تعطیلات نامرتبط به فروشگاه).
- **فیچرهای تاریخی تقاضا**: تأخیرهای ۷/۱۴/۲۸/۳۶۵ روزه و میانگین متحرک ۷/۱۴/۲۸ روزه، همگی ایمن در برابر نشت داده (`shift(1)` قبل از محاسبه‌ی rolling).
- **فیچرهای نوسان‌پذیری** (اضافه‌شده پس از تشخیص مسئله‌ی جهش فروش — در ادامه توضیح داده شده): انحراف معیار متحرک و یک فیچر ضریب تغییرات (`rolling_cv_28`) که میزان نوسان یک سری را، مستقل از سطح فروشش، اندازه می‌گیرد.
- **فیچر نرخ جهش تاریخی**: اینکه یک سری فروشگاه–خانواده چند بار در تاریخچه‌ی خودش یک روز پرت تولید کرده، با یک پنجره‌ی گسترشی ایمن در برابر نشت داده محاسبه می‌شود.

### ۳. پیش‌بینی چندافقی مستقیم
به‌جای یک مدل تک‌مرحله‌ای که به جلو تکرار شود، برای **هر افق (۱ تا ۱۵ روز) یک دیتاست پیش‌بینی مستقیم جداگانه** ساخته می‌شود، هرکدام با فیچرهای تأخیری متناسب با همان افق. این کار از انباشت خطای پیش‌بینی در طول افق جلوگیری می‌کند.

### ۴. مدل
XGBoost (`reg:squarederror`، ۱۰۰۰ درخت، توقف زودهنگام) با پشتیبانی بومی از فیچرهای categorical (`store_nbr`، `family`، `store_type`، `city`، `state`، `store_cluster`).

### ۵. راهبرد اعتبارسنجی
ارزیابی روی **چهار نقطه‌ی شروع پیش‌بینی** در بازه‌ی ژوئن–ژوئیه‌ی ۲۰۱۷. یکی از این نقاط (`۲۰۱۷-۰۷-۱۰`) عمداً **از تمام تصمیمات مربوط به مهندسی فیچر و آستانه‌گذاری کنار گذاشته شد** و فقط یک‌بار، در پایان، به‌عنوان بررسی نهایی تعمیم‌پذیری بررسی شد — برای جلوگیری از بیش‌برازش ناخواسته‌ی تصمیمات طراحی به داده‌ی اعتبارسنجی.

## مسئله‌ی جهش فروش: یک مطالعه‌ی موردی تشخیصی

اعتبارسنجی اولیه نشان داد مدل به‌طور کلی خوب عمل می‌کند، اما زیرمجموعه‌ی کوچکی از روزهای پرحجم را کم‌برآورد می‌کند (حدود ۱.۳٪ از ردیف‌های پرحجم، پیش‌بینی کمتر از نصف مقدار واقعی داشتند). به‌جای رفتن مستقیم سراغ تنظیم هایپرپارامتر، مسیر تشخیصی زیر دنبال شد:

۱. **رد فرضیه‌ی تبلیغات** — ردیف‌های کم‌برآوردشده‌ی شدید و ردیف‌های خوب‌پیش‌بینی‌شده تقریباً نرخ تبلیغات یکسانی داشتند (۹۸.۴٪ در برابر ۹۶.۰٪)، پس `onpromotion` سیگنال گم‌شده نبود.
۲. **یافتن تمرکز در بخش خاص** — ۴۴ تا ۵۶٪ از موارد شدید در خانواده‌ی `CLEANING` بودند (در مقابل حدود ۱۳٪ از جمعیت خوب‌پیش‌بینی‌شده)، و نوع فروشگاه `C` هم به همین شکل بیش‌نمایی داشت.
۳. **یافتن شکاف اطلاعاتی** — ردیف‌های شدیداً کم‌برآوردشده مقادیر تأخیری/میانگین متحرک تاریخی به‌طور سیستماتیک *پایین‌تری* نسبت به ردیف‌های خوب‌پیش‌بینی‌شده داشتند؛ یعنی جهش واقعاً در فیچرهای در دسترس زمان پیش‌بینی، برای همان ردیف‌های خاص، قابل مشاهده نبود.
۴. **اضافه‌کردن فیچرهای نوسان‌پذیری** (`rolling_std_*`، `rolling_cv_28`) برای دادن راهی به مدل جهت تشخیص سری‌های *ذاتاً پرنوسان*، حتی وقتی میانگین اخیرشان عادی به‌نظر می‌رسد.
۵. **اعتبارسنجی با SHAP** — تأیید شد که فیچر جدید نوسان‌پذیری سیگنال واقعی دارد (موارد شدید، ۷۶٪ مقدار `rolling_cv_28` بالاتری نسبت به موارد خوب‌پیش‌بینی‌شده دارند)، هرچند رتبه‌بندی اهمیت فیچر داخلی مدل، وزن کمتری نسبت به فیچرهای مبتنی‌بر سطح (`lag_28`، `rolling_mean_*`) به آن می‌دهد.

این یک یافته‌ی آگاهانه است، نه یک محدودیت پوشانده‌شده: **تابع هدف مدل (خطای مربعی) انگیزه‌ی کمی برای برازش خوب یک زیرمجموعه‌ی نادر و پرنوسان از داده دارد**، حتی وقتی مدل فیچرهایی دارد که می‌توانند کمک کنند. به‌جای برازش اجباری با یک طرح وزن‌دهی مجدد تهاجمی (که ریسک بیش‌برازش روی حدود ۱۲۰ ردیف را دارد)، این پروژه به‌جای آن، راهی برای **علامت‌گذاری صریح** این موارد ساخته است.

## لایه‌ی اطمینان پیش‌بینی

هر پیش‌بینی بر اساس سه‌بخشی (ترسیل) `rolling_cv_28` (نوسان‌پذیری) همان سری در داده‌ی اعتبارسنجی، با برچسب اطمینان `بالا` / `متوسط` / `پایین` مشخص می‌شود — یک آستانه‌ی کاملاً داده‌محور، نه یک برش دلخواه. این ادعا صرفاً بیان نشده، بلکه اعتبارسنجی شده است:

| سطح اطمینان | WAPE | نرخ کم‌برآوردی شدید |
|---|---|---|
| بالا | ۱۰.۴۶٪ | ۰.۴۲٪ |
| متوسط | ۱۴.۳۱٪ | ۱.۸۸٪ |
| پایین | ۴۰.۱۸٪ | ۱۵.۲۲٪ |

این کار یک ضعف شناخته‌شده‌ی مدل را به یک سیگنال عملیاتی تبدیل می‌کند: یک فرآیند برنامه‌ریزی پایین‌دستی می‌تواند با پیش‌بینی‌های با اطمینان `پایین` رفتار متفاوتی داشته باشد (مثلاً موجودی احتیاطی بیشتر، بازبینی دستی) به‌جای اعتماد یکسان به همه‌ی اعداد.

## تفسیر مدل

هم اهمیت فیچر (مبتنی‌بر gain) و هم مقادیر SHAP تأیید می‌کنند که مدل عمدتاً به سطح تقاضای اخیر (`lag_28`، `rolling_mean_7/14/28`، `lag_365`) تکیه می‌کند — سازگار با یک تابع هدف خطای مربعی که برای بخش اصلی داده بهینه می‌شود، نه رویدادهای نادر دم توزیع.

## محدودیت‌ها

- مدل حدود ۱.۱٪ از روزهای پرحجم (بیش از ۱۰۰۰ واحد) را بیش از ۵۰٪ کم‌برآورد می‌کند، که در تعداد کمی از سری‌های فروشگاه–خانواده با تاریخچه‌ی تقاضای ذاتاً پرنوسان متمرکز است.
- این محدودیت به‌عنوان یک محدودیت **شناخته‌شده، اندازه‌گیری‌شده، و علامت‌گذاری‌شده** (از طریق لایه‌ی اطمینان بالا) در نظر گرفته می‌شود، نه یک شکاف بی‌توجه — یک انتخاب آگاهانه به‌جای دنبال‌کردن راه‌حل‌های با بازده نزولی (وزن‌دهی مجدد تهاجمی یا جستجوی نامحدود هایپرپارامتر) که ریسک بیش‌برازش روی چند صد ردیف را دارند.

## پایپ‌لاین استقرار در محیط عملیاتی

آموزش یک مدل خوب یک مسئله است. رساندن خروجی آن به دست کسی که موجودی را برنامه‌ریزی می‌کند — و هیچ‌وقت ترمینال باز نکرده — مسئله‌ی دیگری است که در عمل به همان اندازه مهم است. این بخش به همان مسئله‌ی دوم می‌پردازد.

### معماری

```
train.csv
   │
   ▼  ingestion.py (شبیه‌سازی ورود روزانه‌ی داده)
تاریخچه (روز‌به‌روز تجمیع، با اعتبارسنجی هنگام ورود)
   │
   ▼  validation.py (بررسی schema / مقادیر کلیدی خالی / مقادیر نامعتبر)
   ▼  feature_engineering.py (فیچرهای تقویمی، تأخیری، میانگین متحرک، نوسان‌پذیری)
   ▼  inference.py (بارگذاری مدل XGBoost آموزش‌دیده، پیش‌بینی)
   ▼  decision.py (حذف مقادیر منفی، اتصال سطح اطمینان، علامت‌گذاری ریسک کمبود/مازاد موجودی)
   │
   ▼
report_<تاریخ>.csv — یک فایل قابل‌استفاده برای کسب‌وکار، به‌همراه یک API و یک صفحه‌ی وب
```

هر مرحله یک ماژول پایتون مستقل و تست‌شده در `src/pipeline/` است. `run_pipeline.py` نقطه‌ی ورود واحدی است که همه را به هم وصل می‌کند — یک دستور، کل زنجیره را برای یک تاریخ مشخص اجرا می‌کند.

### لایه‌ی تصمیم کسب‌وکاری

خروجی پایپ‌لاین یک عدد خام پیش‌بینی نیست. هر پیش‌بینی با یک سطح موجودی (که از بیرون تأمین می‌شود) مقایسه می‌شود تا `ریسک کمبود`، `ریسک مازاد`، یا `بهینه` علامت‌گذاری شود — پایپ‌لاین هرگز داده‌ی موجودی نمی‌سازد؛ آن را به‌عنوان ورودی انتظار می‌کشد، دقیقاً همان‌طور که یک سیستم واقعی آن را از یک فید انبار/ERP دریافت می‌کند. یک فایل نمونه‌ی کوچک از موجودی (`data/sample_inventory.csv`) برای نمایش گنجانده شده است.

### رابط وب بدون‌نیاز-به-کد

یک کاربر کسب‌وکاری بدون هیچ پیش‌زمینه‌ی فنی می‌تواند مستقیم از این سیستم استفاده کند:

۱. صفحه‌ی وب را باز کنید.
۲. یک تاریخ انتخاب کنید.
۳. روی «Get Forecast» کلیک کنید.
۴. یک خلاصه‌ی یک‌خطی («۱۵۹ کالا در خطر کمبود موجودی...») و یک جدول کوچک رنگی فقط از موارد نیازمند توجه ببینید.
۵. در صورت نیاز به جزئیات بیشتر، گزارش کامل را به‌صورت CSV دانلود کنید.

بدون خط فرمان، بدون کد، بدون نیاز به تایپ مسیر فایل.

### API

ساخته‌شده با FastAPI:

| Endpoint | کاربرد |
|---|---|
| `GET /` | همان صفحه‌ی وب بدون‌نیاز-به-کد که در بالا توضیح داده شد |
| `GET /forecast?origin_date=YYYY-MM-DD` | پایپ‌لاین را اجرا می‌کند، یک خلاصه‌ی JSON + موارد اولویت‌دار برمی‌گرداند |
| `GET /download?origin_date=YYYY-MM-DD` | گزارش کامل CSV را دانلود می‌کند |
| `GET /health` | بررسی زنده‌بودن سرویس |
| `GET /monitoring` | تاریخچه‌ی اجراهای اخیر پایپ‌لاین (به بخش مانیتورینگ زیر مراجعه کنید) |

### Containerization

این سرویس با Docker بسته‌بندی شده، پس صرف‌نظر از نسخه‌ی پایتون یا بسته‌های نصب‌شده روی سیستم میزبان، دقیقاً یکسان اجرا می‌شود:

```bash
docker build -t favorita-pipeline .
docker run -p 8000:8000 \
  -v ${PWD}/data:/app/data \
  -v ${PWD}/outputs:/app/outputs \
  -v ${PWD}/reports:/app/reports \
  -v ${PWD}/logs:/app/logs \
  favorita-pipeline
```

سپس `http://localhost:8000` را باز کنید.

### مانیتورینگ

هر اجرای پایپ‌لاین — چه از خط فرمان، چه از API، چه از صفحه‌ی وب فراخوانی شده باشد — در `logs/pipeline_runs.jsonl` همراه با زمان، مدت‌اجرا، تعداد ردیف‌ها، و نتیجه (موفقیت یا خطای دقیق در صورت شکست) ثبت می‌شود. `GET /monitoring` اجراهای اخیر را بدون نیاز به باز کردن مستقیم فایل لاگ نشان می‌دهد.

### تصمیمات طراحی قابل‌توجه

- **شبیه‌سازی چرخشی/رو-به-جلو، نه یک تقسیم ثابت یک‌باره.** چون داده‌ی واقعاً جدیدی فراتر از دیتاست اصلی Kaggle وجود ندارد، پایپ‌لاین یک تاریخ انتخابی را «امروز» فرض می‌کند، ورود روزانه‌ی داده تا آن نقطه را شبیه‌سازی می‌کند، و رو به جلو پیش‌بینی می‌کند — نزدیک‌تر به تجربه‌ی واقعی یک سیستم مستقر شده از داده، نسبت به یک تقسیم train/test یک‌باره.
- **عمداً کنار گذاشته‌شده**: Kubernetes، CI/CD پیچیده، زیرساخت ابری، معماری میکروسرویس. هیچ‌کدام مسئله‌ای را که این پروژه واقعاً دارد حل نمی‌کنند (بار یک Container تنها، بدون ترافیک چندسرویسه)؛ اضافه‌کردنشان پیچیدگی بی‌جهت است، نه قضاوت مهندسی درست.
- **`Favorita_GlobalModel.py` (اسکریپت تحقیقاتی/EDA) دست‌نخورده باقی ماند.** منطق مهندسی فیچر پایپ‌لاین، یک تکرار عمدی و مستندشده است که برای استفاده‌ی مجدد و محیط عملیاتی تنظیم شده، نه یک Refactor از اسکریپت تحقیقاتی — این کار دو دغدغه (تحقیق در برابر محیط عملیاتی) را به‌طور تمیز از هم جدا نگه می‌دارد.

## نحوه‌ی اجرا

### ۱. آموزش مدل

```bash
pip install -r requirements.txt
```

فایل‌های CSV دانلودشده از Kaggle را در پوشه‌ی `data/` قرار دهید، سپس اجرا کنید:

```bash
python src/Favorita_GlobalModel.py
```

به‌طور پیش‌فرض، artifact های مدل (مدل آموزش‌دیده، دیتاست‌های پردازش‌شده، پیش‌بینی‌ها) در `outputs/<run_tag>/` داخل خود پروژه ذخیره می‌شوند — بدون نیاز به هیچ تنظیمی. برای هدایت artifact های حجیم به مکان دیگر (مثلاً برای اجتناب از محدودیت فضای ذخیره‌سازی ابری)، متغیر محیطی `FAVORITA_OUTPUT_DIR` را یک‌بار تنظیم کنید؛ در صورت عدم تنظیم، اسکریپت به‌طور خودکار از مقدار پیش‌فرض داخل پروژه استفاده می‌کند.

### ۲. اجرای پایپ‌لاین استقرار

```bash
python run_pipeline.py --date 2017-07-20
python run_pipeline.py --date 2017-07-20 --inventory data/sample_inventory.csv
```

### ۳. اجرای API + صفحه‌ی وب (با Docker)

```bash
docker build -t favorita-pipeline .
docker run -p 8000:8000 -v ${PWD}/data:/app/data -v ${PWD}/outputs:/app/outputs -v ${PWD}/reports:/app/reports -v ${PWD}/logs:/app/logs favorita-pipeline
```

سپس `http://localhost:8000` را باز کنید.
